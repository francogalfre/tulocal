# tutienda — agent instructions

tutienda lets anyone open an online shop by taking photos of a product with their phone. This file covers repo-wide engineering conventions for coding agents. Product and AI-behavior specifics live in `.claude/`:

- `.claude/CONTEXT.md` — what the product is, who it's for, how the seller and buyer flows work. Read it before working on any product feature.
- `.claude/DESIGN.md` — the visual design system. Read it before writing any UI code, component, or copy.
- `.claude/RULES.md` — the behavior spec for the shop's AI sales agent (negotiation, floor price, scam detection, buy handoff). Read it before touching `packages/agents`.

## Stack

Better-T-Stack monorepo, Bun-managed, Turborepo-orchestrated.

| layer | choice |
|---|---|
| runtime / package manager | Bun |
| monorepo | Turborepo, bun workspaces |
| frontend | Next.js 16 (App Router) |
| backend | Hono |
| api | tRPC |
| database | PostgreSQL (Neon), Drizzle ORM |
| auth | Better-Auth |
| ui | Tailwind CSS v4, shadcn/ui (shared via `packages/ui`) |
| env | Varlock |
| lint / format | Oxlint / Oxfmt |
| git hooks | Lefthook |
| deploy | Vercel (web + server as separate services) |

## Layout

```
apps/
  web/            Next.js frontend
  server/         Hono + tRPC backend
packages/
  api/            tRPC routers, business logic
  auth/           Better-Auth config
  db/             Drizzle schema, migrations
  ui/             shared shadcn/ui primitives, design tokens
  agents/         the shop's AI sales agent (empty, build target, see .claude/RULES.md)
  assets/         AI photo-to-listing pipeline (empty, build target, see .claude/CONTEXT.md)
```

`packages/agents` and `packages/assets` are scaffolded but not implemented. They're where the "generate a listing from photos" and "shop agent chat" features described in `.claude/CONTEXT.md` belong.

## Commands

- `bun run dev` — all apps
- `bun run dev:web` / `bun run dev:server` — a single app
- `bun run check` — Oxlint + Oxfmt, run before finishing any change
- `bun run check-types` — TypeScript across all workspaces
- `bun run db:push` / `db:generate` / `db:migrate` / `db:studio`
- `bun run deploy:check` — dry-run a Vercel deploy without uploading

Lefthook runs Oxlint and Oxfmt on staged files at pre-commit. Don't bypass it with `--no-verify`.

## Stack conventions

- **Workspace boundaries.** Shared logic lives in `packages/*`. Never import across `apps/web` and `apps/server` directly. UI primitives come from `@tulocal/ui`, don't duplicate a shadcn component inside an app.
- **tRPC.** Routers live in `packages/api/src/routers`. Use `protectedProcedure` for anything seller-facing (requires auth), `publicProcedure` only for buyer-facing, unauthenticated reads. A public procedure must never return a product's floor price, see `.claude/RULES.md`.
- **Database.** Schema lives in `packages/db/src/schema`, one file per domain concept. Run `db:generate` after editing a schema and commit the generated migration.
- **Env vars.** Each app owns a committed `.env.schema`. Varlock generates `src/env.ts`, import the generated `ENV` accessor, never read `process.env` directly. Run `bun run env:generate` after changing a schema. Real secrets stay in ignored `.env` files or Vercel.
- **Next.js.** `apps/web/AGENTS.md` is regenerated by `next dev`, it flags breaking changes in this Next.js version versus training data. Read it before writing frontend code. Don't delete its content from a diff, it just comes back.

## Code quality

Generic engineering rules. They apply to every package and app in this repo, regardless of feature.

- **Naming.** Every variable, function, and file name is descriptive of what it holds or does, not how it happens to be used or where it came from. No abbreviations that need a lookup, no `data` / `temp` / `item` / `x` when a real name is available.
- **Functions do one thing.** If a function needs "and" to describe it, split it. Prefer several small, well-named functions over one long one with comment banners marking sections.
- **No premature abstraction.** Don't build a generic helper, config layer, or plugin system for a single caller. Two similar call sites can stay duplicated, extract on the third.
- **No dead code.** Delete unused exports, commented-out blocks, and unreachable branches instead of leaving them "just in case." Git history is the fallback, not the working tree.
- **Errors are handled, never swallowed.** No empty `catch` blocks. Either handle the error meaningfully, rethrow it, or let it propagate. Never catch-and-ignore just to silence a type checker or linter.
- **Types are real.** Avoid `any`, prefer `unknown` with narrowing or a proper type. Don't cast to silence an error you haven't understood.
- **No magic values.** A number or string with meaning gets a named constant, not a bare literal repeated across files.
- **No comments in code.** Names and structure carry the meaning. Don't add comments explaining what code does or why, if it needs explaining, rename or restructure it instead.
- **Alias imports, no deep relatives.** Inside `apps/web` and `apps/server`, import from your own app's `src/` with the `@/` alias (`@/components/header`, not `../../components/header`). `packages/*` don't have this alias configured yet, keep those imports relative until it's added, but never write a `../../../` chain, restructure the folder instead.
- **300 lines per file, max.** When a file is about to cross ~300 lines, split it, either a new file next to it or a new folder if it's really a new sub-concern. Don't keep growing one file because it's convenient.
- **Organize by feature, not by layer.** Inside a package or app, group a feature's files together (e.g. a `products/` folder holding its schema, router, and logic) rather than splitting into global `schemas/`, `routers/`, `services/` buckets. `lib/` and `utils/` folders are fine for genuinely shared, cross-feature helpers, not as a dumping ground for feature-specific code.
- **Lint is the floor, not the ceiling.** `bun run check` passing doesn't mean the code is done. Oxlint's `correctness` category is an error, fix it, don't suppress it, but also apply the rules above even where the linter stays quiet.
- **Commits.** Conventional commits only, `type(scope): summary`, one line, matching the existing history (e.g. `feat(bootstrap): ...`). No commit body/description and no `Co-Authored-By` trailer, the subject line is the whole message.
